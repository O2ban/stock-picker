# 性能问题与选股范围需求

## 记录时间

2026-09-21

## 当前已确认的问题

### 1. 全市场默认扫描范围过大

当前页面虽然支持板块选择，但没有真正的可配置选股范围。默认策略会把全部非 ST 股票送入扫描，当前股票池约 5574 只。

用户明确提出：选股范围应在界面中可配置，没必要默认长时间扫描全市场；范围应在扫描开始前生效，以显著减少计算量。

### 2. SQL 单条查询不是主要瓶颈

现有 `daily_kline` 查询按股票代码和日期索引执行，查询计划能够命中 `(code, date)` 主键/索引。

已测量：

- 数据库日线总记录约 9429949 行
- 5574 只股票各读取一次完整历史，约耗时 33.7 秒
- 100 只股票逐只读取日线，约耗时 153 毫秒
- 300 只股票执行默认日线+周线策略，约耗时 1.26 秒，命中 9 条

结论：问题不是某一条 SQL 没有索引，而是全市场扫描的总工作量过大。

### 3. 同一只股票存在重复读取

当前选股引擎在不同条件、评分和结果生成阶段重复调用日线加载逻辑。一只股票在一次选股中可能被读取 2 到 5 次；每次可能读取该股票的全部历史日线，再重新聚合周线和计算指标。

这会造成：

- 数据库读取次数成倍增加
- 943 万行历史数据被反复搬入 Node.js
- 周线聚合和指标计算重复执行
- Node.js 同步计算期间无法及时处理其他 HTTP 请求

### 4. 前端错误表现

长时间同步计算期间，浏览器可能因连接等待过久而出现：

```text
Failed to fetch
```

此前还出现过：

```text
Unexpected token '<', "<html>..." is not valid JSON
```

其原因是代理超时后返回 HTML 错误页，前端把 HTML 当作 JSON 解析。当前前端已增加非 JSON 响应提示，Nginx `/stock-picker/` 代理读写超时已设置为 180 秒，但这只是缓解表现，不是根本性能方案。

## 新增产品需求：界面可配置选股范围

选股页面需要增加“选股范围”配置，让用户在执行前明确限定扫描对象。范围配置应在后端获取股票列表之后、选股计算之前生效，不能先全市场计算再过滤。

至少需要考虑：

- 板块范围
- 股票数量范围或扫描上限
- 是否只扫描最近有数据、数据完整的股票
- 可按股票代码、股票名称选择或排除
- 结果数量与扫描数量分开配置

具体界面字段和默认值待后续设计确认。默认行为应避免无提示地长时间扫描全部股票。

## 后续优化方向

按优先级考虑：

1. 先实现界面可配置选股范围，让用户主动缩小扫描股票池。
2. 同一轮选股中每只股票只加载一次日线数据，日线、周线、评分和结果展示复用同一份数据。
3. 只加载指标所需的最近历史窗口，避免读取 2018 年以来的全部日线。
4. 复杂或大范围选股再考虑改为后台任务，前端通过任务状态获取结果。
5. 长期可考虑批量读取和指标缓存。

## 当前约束

- 保持日线和周线选股结果口径不变。
- 继续只读复用 kline-trainer 的 `kline.db` 和 `better-sqlite3`。
- 不在 stock-picker 创建新的行情数据库。
- 先确认范围配置方案，再逐项实施性能优化。
